# オンラインDDLでインデックスを貼る際の考慮事項

- テーブルにインデックスを貼るときに、オンラインDDLを利用できる場合がある。
- オンラインDDLを行えるかどうか、行う場合は何に気をつければよいかのまとめ。
- 参考
- [第30回　InnoDBオンラインDDLについて | gihyo.jp](https://gihyo.jp/dev/serial/01/mysql-road-construction-news/0030)
- [第180回　MySQLのメタデータロックについて | gihyo.jp](https://gihyo.jp/article/2022/09/mysql-rcn0180)
- [第209回 MySQLのALTER TABLEステートメント実行時の注意点 | gihyo.jp](https://gihyo.jp/article/2023/11/mysql-rcn0208)
- **オンラインDDLとは**
- MySQL 5.6以降から使える、DBを停止させずにALTER TABLEできるMySQLの機能
- **オンラインDDLを行えるかどうか**
- 詳しくは：[第30回　InnoDBオンラインDDLについて | gihyo.jp](https://gihyo.jp/dev/serial/01/mysql-road-construction-news/0030)
- [MySQL :: MySQL 8.0 リファレンスマニュアル :: 15.12.1 オンライン DDL 操作](https://dev.mysql.com/doc/refman/8.0/ja/innodb-online-ddl-operations.html) にある下記の表で、「インプレース：はい」かつ「同時 DML の許可：はい」であれば(基本的には)その操作はオンラインDDLで行うことができる。
- (オンラインDDLできる操作の場合、オプションなどを特に指定しない限りは勝手にオンラインDDLになる)

| --- | --- | --- | --- | --- | --- |
| セカンダリインデックスの作成または追加 | いいえ | はい | いいえ | はい | いいえ |
| インデックスの削除 | いいえ | はい | いいえ | はい | はい |

- 上記の表でオンラインDDL対象の操作であっても、マイグレーション対象のテーブルがMySQL5.5以前に作られた場合や、同時に他のオンラインDDLでないテーブル定義変更を行う場合などは対象外になったりする。
- **行う場合は何に気をつければよいか**
- **1. 本当にオンラインDDLしてくれるのかどうかを確認**
- 詳しくは：[第30回　InnoDBオンラインDDLについて | gihyo.jp](https://gihyo.jp/dev/serial/01/mysql-road-construction-news/0030)
- ALTER TABLE文には動作オプションを付けることができ、 `ALGORITHM=INPLACE,LOCK=NONE`  と付けるとインプレース方式かつロックを取らずに(= つまりオンラインDDLで)ALTER TABLEするように指示できる。
- `CREATE INDEX`文には付けられないので、`ALTER TABLE table_name ADD INDEX ...` のようにALTER TABLE文を使って張ろう。
- 逆に、デフォルトの動作がオンラインDDLな操作であっても末尾に `ALGORITHM=INPLACE`, `LOCK=NONE` を付けることで、なにかの原因で実はオンラインDDLじゃなかったときにエラーを吐いてくれるのでミスを防げる。
- Railsのマイグレーションでこれを指定する方法は2024/05現時点では無さそうだった。生クエリ発行すれば行けそう。
- **2. ALTER TABLE文の前後で他に重いクエリを流していないことを確認**
- 詳しくは：[第209回 MySQLのALTER TABLEステートメント実行時の注意点 | gihyo.jp](https://gihyo.jp/article/2023/11/mysql-rcn0208)
- オンラインDDLの最中はロックを取らないが、オンラインDDLの開始時と終了時には一瞬だけロックをとる。
- このとき、他にそのテーブルを見ているクエリが実行中の場合、そのクエリが終わり次第ロックを取る。
- オンラインDDLの開始時と終了時に他に重いクエリ(クエリA)が流れていたりすると、そのクエリAが終わるまでロック取得待ち状態になってしまう。
- このオンラインDDLがロック取得待ち状態のとき、更に他の同じテーブルを見るクエリ(クエリB)が発行された場合、「クエリAを待っているオンラインDDLを待っているクエリB」が出てきてしまい、クエリAが完了するまでクエリBまで待たされてしまい、サービスに影響が出る場合がある。
- なので、オンラインDDL実行時は他に同じテーブルを見る重いクエリが流れていないかを確認する必要がある。
- **3.  index作成中の書き込みを溜めるログファイルの容量の確認**
- 「index作成中の書き込みを溜めるログファイルの容量」と
- 「対象テーブル1レコードあたりのデータ量」を確認し、
- 「オンラインDDL中に溜められる書き込みの件数（＝ログファイルの容量／対象テーブル1レコードあたりのデータ）」が十分かどうかを確認する。
- ログファイルの容量は  `SHOW VARIABLES LIKE 'innodb_online_alter_log_max_size' ;` で確認できる。
- 対象テーブル1レコードあたりのデータ量は [MySQL :: MySQL 8.0 リファレンスマニュアル :: 11.7 データ型のストレージ要件](https://dev.mysql.com/doc/refman/8.0/ja/storage-requirements.html) を基に計算できる。
- (大抵の場合は問題無さそう)
- (オーバーすると`DB_ONLINE_LOG_TOO_BIG`というエラーがでるらしい)
- **4. デプロイのタイムアウト時間の確認**
- デプロイにタイムアウトが設けられている場合、その時間内に終わりそうかを確かめておく。
- **5. index作成中のパフォーマンスへの影響の確認**
- レコード数320万ほどのテーブルであっても、マイグレーション時のI/Oの急上昇により、RDS全体のレイテンシが落ちる場合がある。
- 「レコード削除が起きているテーブルかどうか」「インデックスを付与するカラムの型」なども関わってきそうで、事前にパフォーマンスを予想するのは難しそう。
