- ユーザーpc <=> adminサーバー <=> webサーバー があるのを想定。ユーザーPCから繋げて、webサーバーを操作したい
  - adminにsshできるとき
    - = adminにOpenSSHが入っていて、22番port(= sshができるポート)が空いているとき
    - nc(netcat)コマンドの機能で操作
      - adminかユーザーpcにncコマンドが必要
```ssh_config
Host web_server
  ProxyCommnad ssh (webサーバーのip) nc %h %p
```

- ssh標準の機能でもできる
  - `ProxyCommand ssh -W %h:%p (webサーバーのip)`
  - `-W`オプション
    - [ProxyCommandによるsshの多段接続について -- ぺけみさお](https://www.xmisao.com/2013/10/08/ssh-proxy-command.html)
- adminにsshはできないが、adminは[httpプロキシ](8080番port)が使える時
  - `ProxyCommand connect -H (adminのip):8080 %h %p`
- adminにsshはできないが、[socksプロキシ](1080番port)が使える時
  - `ProxyCommand connect -S (adminのip):1080 %h %p`
- ユーザー => web はすべて閉じられていて、admin => web は、webサーバーのwebのポート(80番port)のみ空いていて、ここで情報を配信しているようなとき（ユーザーからwebサーバーの80番portにアクセスしたい）
  - ポートフォワーディング
    - `ssh (adminサーバーのip) -L 10080:(webサーバーのip):80 -N`
    - ユーザーPCのローカル(L)の10080番portが、webサーバーの80番portに繋がる
    - ユーザーPCのブラウザとかで、`http://localhost:10080`でwebサーバーの80番にアクセスできる
- adminはwebにアクセス(port番80)できないが、adminサーバーでwebからなにか落としたい、というとき
  - httpプロキシ(8080番port)を使う設定の箇所に、ローカルの別ポートを指定して、その別ポートとユーザーPCの8080番ポートを繋げる
  - `export http_proxy="http://localhost:9090"`
  - `ssh (adminサーバーのip) -R 9090:(ユーザーPCのip):8080 -N`
- webサーバーの80番portで情報を配信しているけれども、ポートフォワーディングだとURIが変わってしまい嫌だ、というとき
  - socksプロキシで(= ダイナミックポートフォワーディングとも言う)、ユーザーpcの1080番portを全てadminサーバーのtcp通信に移し替える
  - `ssh (adminサーバーのip) -D 1080 -N`
    - `-D`で、ローカルサーバーのどのポートをリモートに転送するかを指定(socksプロトコルののデフォルトだと1080番)
    - `-p`は、リモートのどのポートに転送するか指定する(デフォルトで22番?)
    - > -p port
      - >Port to connect to on the remote host.  This can be specified on a per-host basis in the configuration file.
  - ブラウザ側やプログラム側でも、socksプロキシを使いますよ、という設定が必要
  - URIはそのままのものを使える(localhost: と指定する必要がない)

- **Ethernet**
  - データリンク層
  - 送信元MACアドレスは自分の機器のもの
  - 宛先MACアドレスは、**自身が属するネットワーク内での宛先**のMACアドレスを指定
  - その宛先の機器で(ルーターとか)、更に宛先MACアドレスが書き換わって、別ネットワークのルーターに届き、、、が繰り返される
- **IP**
  - ネットワーク層
  - 送信元IPアドレスは自身のIPアドレスで、無ければDHCPで要求する
  - プライベートIPアドレスのときはNATみたいなのが使われて、ポートに対応が化けて送られるのかも?
- **UDP**
  - トランスポート層
  - ポート番号くらいしか入ってない
- **TCP**
  - トランスポート層
  - 通信確立時
    - PC➡NWへ、SYN(転送許可要求)のFLAG
    - PC⬅NWへ、↑に対してのACK(転送許可)とSYNのFLAG
    - PC➡NWへ、↑に対してのACKのFLAG
  - 通信の確実性のために「シーケンス番号」と「ACK番号(確認応答番号)」を送り合う
    - 通信確立時
      - シーケンス番号は、送り始めではランダム値を送る
        - PC➡NW, PC⬅NW のどちらの場合も。なのでランダム値が2回生成されている
      - 返送側は、送られてきた`シーケンス番号 + 1`をACK番号に入れて返す
    - 通信時
      - シーケンス番号に、直前に受け取ったACK番号を入れて送る
      - ACK番号には、`直前に受け取ったシーケンス番号 + 直前に受け取ったウィンドウサイズ`を入れて送る
        - これにより、次に欲しいデータのバイトアドレスを伝えられる
  - 上位層をセグメント化させて、何度かに分けて 送った&送られた のやりとりをする
  - ウィンドウサイズをいい感じにやりとりして、相手の処理可能なバッファに合わせてデータを送る(理解が曖昧)
  - セグメントが揃ったときはFLAGのPSH(即時に上位層に転送)を立てる
  - 通信終了時
    - PC➡NWへ、FIN(終了要求)のFLAG
    - PC⬅NWへ、↑に対してのACKとFINのFLAG
    - PC➡NWへ、↑に対してのACKのFLAG
- **DHCP**
  - アプリケーション層のプロトコル
  - IPアドレスの割り振りを要求する
  - データリンク層もネットワーク層も全部ブロードキャスト、トランスポート層はUDP
  - ポートは67,68
  - 手順
    - クライアントが DHCP サーバーを見つけるための`DHCP DISCOVER`
    - DHCP サーバーがクライアントに割り振るアドレスを提示する`DHCP OFFER`
    - クライアントがその候補から要求する IP アドレスを伝える`DHCP REQUEST`
    - サーバーがその要求を認める`DHCP ACK`

    - ドメインのアドレス
  - CNAME
    - あるドメインの標準ドメイン名
      - 知りたいドメインの標準ドメイン名のAレコードを見ればアドレスがわかる
      - `blog.example.com`のCNAMEは`example.com`だったはず
  - NSレコード
    - あるドメインのネームサーバーのドメイン
  - SOAレコード
    - プライマリーなネームサーバー？ 謎
  - AAAAレコード
    - IPv6のドメインのアドレス
  - MXレコード
    - メールはここに送ってね、のドメイン

**proxy.rb**

```
require "socksify"
require "open-uri"
Socksify::proxy("127.0.0.1", 5678) { URI.open('https://httpbin.org/ip').read }
```
