# 大規模なマイグレーションを行う際の手順

- インデックス追加とか。
- マイグレーションに限らず、大きなバッチ処理やインフラ移行を行うときにも応用できるはず。
- **反映手順**
- (下記をテンプレにして、実際に行う際は各手順をもっと具体的に準備しておく)
- **反映日時を決める**
  - 決め方
    - 時間の検討
      - ヘルプの求めやすさ
      - リクエスト数
      - jobの影響
        - なにか定期jobを実行中か
        - その後直近に定期jobが控えていないか (復旧用の時間を確保したい)
    - 曜日の検討
      - 金曜日は避ける
- **手順をまとめる**
  - 実行中のクエリが無いことを確認する
    - リードレプリカからだと見れないかも？コンソールでmysql入って確認しよう
```sql
-- SHOW PROCESSLISTを整えたものを見るクエリ
SELECT * FROM information_schema.PROCESSLIST WHERE COMMAND != 'Sleep' ORDER BY TIME DESC;
```

- リリースPRをマージする
- CIが走り、完了したことを確認する
- 完了したことを確かめるクエリを発行し、念の為確認する
  - `SHOW INDEX FROM table_name;`
- **反映時に不具合が起きたときの対応をまとめる**
  - 不具合想定：マイグレーションのCIが終わらないとき
    - ↓等を調べて対応を考えておく
      - タイムアウトの有無
      - タイムアウト時のマイグレーションの中断・続行の挙動確認
  - 不具合想定：タイムアウトやエラーによってCIが中断された場合
    - **マイグレーションの状態(完了・実行中・中断)を確認する**
      - `SHOW INDEX FROM table_name;`
        - インデックスが貼ってあった場合 → **完了**
        - 貼っていない場合 → マイグレーションが現在実行中かどうかを確認する
      ```sql
      SELECT * FROM information_schema.PROCESSLIST WHERE COMMAND != 'Sleep' ORDER BY TIME DESC;
      ```
      - `CREATE INDEX ...` 文がある場合 → **実行中**
      - ない場合 → **中断**
- **完了していた場合**
  - 不具合後もマイグレーションは走り続けていたということになるので、念の為schema_migrationも最新になっているか確認して、完了
    - もしschema_migrationが最新でない場合、手動でschema_migrationのレコードを追加する
- **実行中だった場合**
  - あらかじめ、どれくらい待つかを決めておく
  - 決めていた時間が経っても終わらないときは、mysqlに入ってマイグレーションプロセスをKILLする
    - 手順 (具体的な方法は状況次第)
      - PRD環境に入る
      - railsに入ってDBの接続情報(URL, PW)を見る
      - mysqlに入る
        - `mysql -h (DATABASE_URLで見たURL) -u (ユーザー名) -p (DB名)`を打って、見たパスワードを入力する
      - マイグレーションのプロセスIDを見つける
        - `SELECT * FROM information_schema.PROCESSLIST WHERE COMMAND != 'Sleep' ORDER BY TIME DESC;`
      - マイグレーションのプロセスをKILL
        - `KILL (上記クエリで見つけたマイグレーションのプロセスのID)`
  - このままだと次回のデプロイ時にまたマイグレーションが走ってしまうので、このPRのrevertPRを作り、反映させる
  - (後日) 中断された原因を調査して対応を考える
- **中断されていた場合**
  - このままだと次回のデプロイ時にまたマイグレーションが走ってしまうので、このPRのrevertPRを作り、反映させる。
  - (後日) 中断された原因を調査して対応を考える
- 不具合想定：DBの負荷が高まった場合
  - slackにDBのCPUのアラート等がくる
  - あらかじめ、どれくらい待つかを決めておく
  - 決めていた時間が経ってもアラートが出続けるときは、マイグレーションプロセスのKILLとrevertPRの反映を行う
  - (後日) 対応を検討する
- **作業後に記録すること**
- 今後のために、下記2点を記録しておく
  - マイグレーションにかかった時間
    - クエリ・レコード数・DBの性能と共に
  - マイグレーション中のDBのCPU使用率の推移
