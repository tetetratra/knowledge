# API設計

- 新機能を作るときは、既存のAPIに載っかれないかを検討する
  - 新たに「(機能名)API」ではなくて、既存の「ホーム画面API」のパラメータを増やすなどして対応したい
- 機能`hoge`があったとき、
  - `hoges_controller.rb` (`HogesController`)
  - `hoges/fugas_controller.rb` (`Hoges::FugasController`)
  - のように、`hoges`の`s`まで一致させるようにnamespaceを切ると、ファイル名的に前方は一致するので良い
    - 名前空間やURLに`s`がついてしまうのがネック
- 列挙型のような値を受け取るパラメータは、suffixを`_type`とするとよい
  - 例：`{ from_date_type: 'today' }`
- **リソースはなにか**を意識してURLを組み立てよう
  - 必ずしもDBのテーブルとURLが一致している必要はない
  - DBのテーブルには(ユーザーデータなら)`user`を入れるとよいけれど、URLには`user`は入れなくていい
    - ユーザーデータなことは自明なので
- バリデーションエラー時のレスポンス
  - `200`で`{ status: false, error_message: '...' }`方式
    - 予期**している**エラーのときにはこっち
    - 名前は`result`よりも`status`の方が意味がある名前なのでよい
  - `400`方式
    - 予期**しない**エラーのときにはこっち
    - エラートラッキングシステム(rollbarとか)上の400が増えてしまう
- POSTのAPIのレスポンスでは、保存後の値を返してあげるとよい
  - フロント側は保存後の値を使ってもらえば、画面とDB間で不一致という現象が起こりにくくなるため
- 特にフロントとサーバーを別々に開発しているときは、作る予定のAPIがどの画面でどれくらいの頻度で呼ばれるかを把握しておこう
- 集計結果系のデータを返すAPIは`/api/リソース名/dashboard`のようなURLがよさげ
  - たとえ1個の集計結果しか返さないとしても、`/api/リソース名/集計結果名`のようにしてしまうと、今後別の集計結果を返したくなったときにわざわざ新しいAPIを作らなければならなってしまう。
- 雑多な色々を入れるAPI (ホーム画面APIなど) では、レスポンスパラメータで名前空間を切ると良い
```json
{
  'foo': { // 機能やモデルfooに関する値
    'xxx': ...,
    'yyy': ...
    'count': ...
  },
  'bar': { // 機能やモデルbarに関する値
    'aaa': ...,
    'bbb': ...,
    'count': ...
  }
  // フラットに { foo_xxx, ..., foo_count, ..., bar_count } とやるよりも名前空間で分けた方がわかりやすくなる
}

```

- 同じ値を複数のAPIから取れるのは、できればやめたほうがいい
- 値をキャッシュしてもってAPIを叩く回数を減らす術がある
  - 計算は重いがあまり変更が起きないようなデータに
- アプリ←→サーバー間で、それぞれのAPI設計に関する考え方をあらかじめどこかで共有(文書化など)すれば、設計の議論中に決断を下しやすくなる
- **外部API呼び出し**をする処理はrate limitに注意
  - rate limitがどれくらいかを調べておく
  - 今から作るAPIがどれくらいの回数・頻度で叩かれるかを見積もっておく
