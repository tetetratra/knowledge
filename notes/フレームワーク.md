# フレームワーク

- 漠然とした課題があるとき、「目的」を更に下記の3つに分解して定義するとよい
  - **成果 / Outcomes**
    - 視点：実施者
    - 実際に得られたアウトプット
    - 何ができたか
  - **成功基準 / Success Criteria**
    - 視点：組織や関係者
    - 成果が十分かどうか
    - 「評価軸」「達成ライン」
  - **提供価値 / Value**
    - 視点：利用者・顧客の視点
    - 相手にとって何が嬉しいか
- 思考フレームワークの一覧
  - **緊急度・重要度マトリクス**
    - タスクを「緊急度」と「重要度」の2軸で4象限に分け、優先順位を決める
    - 「重要だが緊急でない」第2象限に時間を割くことが成果につながるとされる
    - 使用例：週初めにタスクを4象限に振り分け、第4象限（緊急でも重要でもない）の定例資料づくりをやめる
    - 使用例：割り込み依頼が来たとき、いまの作業と同じ象限に置いて比べ、どちらを先にやるかを決める
  - **GROWモデル**
    - コーチングで使う会話の型で、Goal（目標）→ Reality（現状）→ Options（選択肢）→ Will（意思・行動）の順に問いかける
    - 答えを教えるのではなく、相手が自分で行動を決められるように導く
    - 使用例：1on1で「半年後どうなっていたいか」から始め、最後に「来週までに何をやるか」を本人に決めてもらう
    - 使用例：自分のキャリアの悩みを、4つの問いに順に答えて整理する
  - **バリューチェーン分析の社内運用版**
    - 業務を一連の活動に分け、どの活動が価値を生み、どこにコストや手間がかかっているかを見える化する
    - 本来は企業の競争優位を分析する手法で、それを社内の業務フローに当てはめて使う
    - 使用例：問い合わせ受付から解決までの工程を並べ、顧客満足に効いていない工程を洗い出す
    - 使用例：開発の要件定義からリリースまでの各工程に工数を書き出し、改善する箇所を選ぶ
  - **AIDMA**
    - 消費者が購買に至るまでの心理の流れで、Attention（注意）→ Interest（関心）→ Desire（欲求）→ Memory（記憶）→ Action（行動）の5段階からなる
    - どの段階で離脱しているかを特定し、段階ごとに施策を考える
    - 使用例：社内ツールの利用が広がらない原因を「存在が知られていない」（Attention）のか「使う動機がない」（Desire）のかに切り分ける
    - 使用例：LPの構成を、5段階の順に情報を並べて設計する
  - **KPIツリー**
    - 最終目標（KGI）を、それを構成する要素に分解して木構造にし、行動できる指標（KPI）まで落とし込む
    - 足し算・掛け算で分解すると、漏れや重複を防ぎやすい
    - 使用例：売上を「訪問者数 × 購入率 × 客単価」に分解し、どの指標を伸ばすかを決める
    - 使用例：「障害対応時間の短縮」を「検知までの時間」と「復旧までの時間」に分け、それぞれに指標を置く
  - **SMART**
    - よい目標が満たすべき条件で、Specific（具体的）・Measurable（測定可能）・Achievable（達成可能）・Relevant（関連性）・Time-bound（期限）の5つ
    - 曖昧な目標を、達成したかどうかを判定できる形に直すときに使う
    - 使用例：「テストを充実させる」を「3月末までに主要APIのテストカバレッジを80%にする」に書き直す
    - 使用例：チームメンバーの目標設定シートを、5つの観点で見直す
  - **PERT図**
    - 作業の依存関係と所要時間をネットワーク図で表し、プロジェクト全体の最短期間を割り出す
    - 遅れると全体が遅れる経路（クリティカルパス）を特定できる
    - 使用例：リリースまでの作業を図にし、デザイン待ちがクリティカルパスになっていると分かって先に着手する
    - 使用例：楽観値・最頻値・悲観値の3点で見積もり、スケジュールのバッファを決める
  - **RACI**
    - タスクごとに、Responsible（実行責任者）・Accountable（説明責任者）・Consulted（相談先）・Informed（報告先）を割り当てる表
    - 「誰がやるのか」「誰が決めるのか」という曖昧さをなくす
    - 使用例：複数チームが関わる移行プロジェクトで、作業ごとにRACIを作り、承認者を1人に決める
    - 使用例：「決まったことを知らされていない」という不満が出たとき、Informedが漏れていないかを確認する
  - **ムリ・ムラ・ムダ**
    - トヨタ生産方式に由来する、業務の非効率を見つけるための3つの観点
    - ムリは負荷が能力を超えている状態、ムラは負荷が時期や人によってばらつく状態、ムダは価値を生まない作業を指す
    - 使用例：月末にだけ作業が集中する「ムラ」を見つけ、作業の一部を月中に前倒しする
    - 使用例：同じ情報を複数のシステムに手入力している「ムダ」を洗い出し、自動化する
  - **ECRS**
    - 業務改善の4原則で、Eliminate（排除）→ Combine（結合）→ Rearrange（入れ替え）→ Simplify（簡素化）の順に検討する
    - 効果の大きい「そもそもやめられないか」から先に考える点に特徴がある
    - 使用例：週次の報告会議を、まず「やめられないか」（E）を検討し、だめなら別の会議との統合（C）を検討する
    - 使用例：デプロイ手順を見直し、手動の確認作業をなくせるか、まとめられるかを順に検討する
  - **動機づけ・衛生理論**
    - ハーズバーグによる理論で、仕事の満足を生む「動機づけ要因」と、不満を防ぐ「衛生要因」を分けて考える
    - 動機づけ要因は達成・承認・仕事そのもの・責任など、衛生要因は給与・労働条件・人間関係・会社の方針などを指す
    - 衛生要因を改善しても不満が減るだけで、意欲が高まるとは限らない
    - 使用例：メンバーの意欲が低いとき、待遇の改善（衛生要因）だけでなく、裁量や承認の機会（動機づけ要因）を増やす
    - 使用例：退職理由のヒアリング結果を2つの要因に分類し、打ち手を分けて考える
  - **PREP**
    - 結論を先に伝える話し方・書き方の型で、Point（結論）→ Reason（理由）→ Example（具体例）→ Point（結論）の順に話す
    - 聞き手が要点をすぐにつかめ、短い時間でも伝わりやすい
    - 使用例：上司への報告を「結論：A案を推します → 理由：コストが半分 → 例：試算では… → 改めてA案で進めたい」の順で話す
    - 使用例：Slackでの技術的な提案を、PREPの順に書いて長文でも読まれるようにする
