# 動画

- [Rails + AWS でモバイルフレンドリーな動画配信サイト構築](https://tech.medpeer.co.jp/entry/2018/01/18/174542)
  - 背景・課題
    - 従来のシステムではCloudFrontでキャッシュしづらく、通信状況によってはファーストビューまでに時間がかかりサイト離脱につながっていた
    - IE Edgeの特定バージョンでリファラ参照ができない仕様上の問題があった
  - 観点
    - モバイルフレンドリーな再生体験
      - 通信状況に応じた適応ビットレート配信で、ファーストビューまでの時間を短縮
    - 直リンク禁止（コンテンツ保護）
      - 署名付きURL/Cookieの使い分けによるアクセス制御
  - 構成
    - 管理者がMP4をS3（rawバケット）にアップロードすると、Lambdaが起動しElastic TranscoderがHLS形式に変換する
    - 複数ビットレート（600k、1M、2M）で出力し、ABRに対応
    - 変換後のHLSファイルはS3（processedバケット）に格納され、CloudFront経由で配信される
    - フロントエンドではhls.jsでHLSストリーミング再生を行う
    - バックエンドはRailsで構築
  - アクセス制御
    - MP4ファイルには署名付きURLを使用し、HLS（m3u8 + tsセグメント）には署名付きCookieを使用することで直リンクを禁止した
    - ユーザー認証と組み合わせ、認証済みユーザーのみが動画にアクセスできる構成にしている
- [ママリでAWSを使った動画配信をはじめました。](https://tech.connehito.com/entry/2020/05/12/143906)
  - 背景・課題
    - ママリ内の人気記事を動画化して配信する施策を開始するにあたり、動画配信基盤を新規構築する必要があった
    - DRMは不要、シンプルな要件での構築を目指した
  - 観点
    - 低コスト
      - サーバーレス構成で運用コストを最小化
    - 構成のシンプルさ
      - 最小限のAWSサービスの組み合わせで立ち上げる
  - 構成
    - 管理者がMP4をS3にアップロードすると、API Gateway + Lambdaを経由してMediaConvertのジョブが起動する
    - MediaConvertがMP4をHLS形式に変換し、同時に1秒おきのJPEGキャプチャ画像を生成する
    - 変換後のHLSファイルはS3に格納され、CloudFront経由でクライアントに配信される
    - 動画のメタデータはDynamoDBで管理する
  - 技術選定
    - 配信形式はHLSを採用。MPEG-DASHよりシンプルで、iOS/Androidのネイティブ再生に対応しており、Safariで直接再生可能なため
  - 大量処理への対応
    - 200本以上・合計2時間超の動画を処理する必要があった
    - Node.jsスクリプトで最大10並列のアップロードを実装し、MediaConvertの並列変換により約16分で全変換が完了した
  - コスト実績
    - 60分の動画変換が約218円、100GBの配信で約1,220円
    - S3・Lambda等はほぼ無料枠内に収まった
- [1秒動画のつくり方 ― 「家族アルバム みてね」における動画エンコードパイプラインとその最適化事例](https://gihyo.jp/article/2023/07/mitene-07-1sec-movie)
  - 背景・課題
    - 「家族アルバム みてね」では、ユーザーの写真・動画から自動でダイジェスト動画（1秒動画）を生成する機能を提供している
    - 3種類（四季版/月版/年間版）があり、大量配信期間（例: 4月15日から1週間で全家族への配信完了）における効率的な生成・配信が課題だった
  - 観点
    - 大量処理のスループット
      - 全家族に期限内（1週間）に届けるという配信SLA
    - 成果物の段階的デリバリー
      - 全員分の完了を待たず、完成した家族から順次配信する
    - 計算リソースの均一利用
  - 構成
    - BigQueryで対象家族を抽出し、ルールベースで素材を選択した後、transcoderマイクロサービスが動画エンコードを実行し、プッシュ通知で配信する
    - transcoderはEKS + EC2上で動作し、FFmpegによるエンコード処理をSidekiq Batchでパイプライン化している
      - パイプライン内のWorkerは、Trim（動画切り出し）→ Effect（エフェクト付与）→ Add Watermark → Crossfade（連結）の順に実行される
  - 最適化: 成果物の完成遅延を防ぐ工夫
    - 当初は「全家族のステップA → 全家族のステップB → ...」の順で実行しており、最後のステップ完了まで誰の動画も完成しなかった
    - パイプライン先頭の優先度を下げ、「家族1のフルパイプライン → 家族2のフルパイプライン」の順に変更することで、成果物がコンスタントに段階的に出力されるようになった
  - 最適化: リソース利用の均一化
    - 各ステップのCPU/メモリ要求量に大きな差があった（TrimはI/O待ち中心、Crossfadeはメモリ消費大）
    - キューを分離して優先順位制御を導入することで、各種ステップが常時並行処理され、計算リソースの利用が安定した
- [ABEMAの動画配信システムを理解する](https://developers.cyberagent.co.jp/blog/archives/49162/)
  - 背景
    - ABEMAは10個超のマイクロサービスがKubernetes上で稼働する大規模動画配信プラットフォーム
    - Go言語で開発されたマイクロサービス群がgRPCで通信し、Grafana + Prometheusで監視している
  - 観点
    - 運用の安定性
      - 大規模サービスを止めないための監視・アラート体制
    - 可観測性
      - CDN帯域・サービスメトリクスのリアルタイム可視化
    - 運用担当者のセルフサービス化
      - エンジニアへのエスカレーションなしで対応可能にする
  - CDN帯域監視の仕組み
    - CDNの帯域情報をAPIで定期取得し、Prometheus Exporterに送信してGrafanaダッシュボードで可視化する
    - 閾値を超えた場合はWebhookで通知する
  - ライブ配信デバイスの管理
    - 管理画面のフロントエンドからgRPC経由でバックエンドサービスにリクエストを送り、AWS SDKを通じてMediaLive APIでElemental Linkデバイスを制御する
    - これにより運用担当者が直接デバイスを再起動でき、エンジニアへのエスカレーションが不要になった
  - DRMライセンスプロキシの改善
    - DRMリクエスト時、初期段階では内部のコンテンツIDが不明で、レスポンス処理時に初めて判明するという課題があった
    - Goのhttputil.ReverseProxyを活用し、リクエストコンテキストにContentオブジェクトポインタを事前挿入。Directorでリクエスト生成、ModifyResponseでレスポンスからコンテンツ情報を取得・更新する設計で解決した
- [AWS CloudFront+S3で動画アップロードからHLSストリーミング再生できるようにしてみた](https://zenn.dev/smartcraft/articles/video-upload)
  - 背景・課題
    - 製造現場向けSaaSプロダクトに動画アップロード・再生機能を新規実装する必要があった
  - 観点
    - セキュリティと自動化の両立
      - HLSのセグメント分割特性に対して署名付きCookieで保護しつつ、アップロードから配信までを完全自動化
    - サーバー負荷の回避
      - S3直接アップロードにより、アプリケーションサーバーを経由しない設計
  - 構成
    - アップロード時は、バックエンド（Rails）がS3の署名付きURLを生成し、フロントエンド（React）がaxios.putでS3に直接アップロードする
    - S3へのアップロード完了をトリガーにLambdaが起動し、MediaConvertでHLS形式（.m3u8 + .tsセグメント）とサムネイル（JPEG）を生成する
    - 再生時は、バックエンドがRSA秘密鍵でCloudFrontの署名付きCookieを生成し、react-playerがwithCredentials=trueでCloudFront経由のHLSストリーミングを行う
  - HLS再生とセキュリティの両立
    - HLSでは複数の.tsセグメントファイルが順次読み込まれるため、ファイルごとの署名付きURLでは管理が困難だった
    - CloudFrontの署名付きCookieを採用することで、1つのCookie設定でインデックスファイルと全セグメントファイルへのアクセスを一括許可する設計にした
      - Cookie生成時にBase64エンコード後の特殊文字（+, /, =）を（-, _, ~）に変換する必要がある
      - リソースパターンにワイルドカード（*）を使い、.m3u8と.tsの両方を許可する
- [プライベートで動画配信システムを内製化して2年運用した話](https://techtekt.persol-career.co.jp/entry/tech/251212_02)
  - 背景・課題
    - 教室ビジネスの生徒向けオンデマンド動画配信にVimeoを利用していたが、年間1,000件規模のアップロードで月額コストが高額化していた
  - 観点
    - ランニングコストの最小化
      - Vimeoの月額コストからの脱却が最大の動機
    - 段階的な最適化
      - 処理時間・コスト・スケーラビリティのトレードオフを4世代かけて検証
  - 4世代にわたる技術変遷
    - Ver1（Lambda + FFmpeg）: サーバーレスで低コストだったが、Lambdaの処理時間上限15分に抵触し、数GBの動画を処理できなかった
    - Ver2（AWS MediaConvert）: 安定した処理が可能になったが、月額数万円のクラウドコストが発生した
    - Ver3（VPS + CPU H.264）: クラウド従量課金を回避できたが、CPUのエンコード性能に限界があり同時処理数が稼げなかった
    - Ver4（オンプレGPU + AMD RX 7600）: AMFハードウェアエンコーダーにより、従来30分以上かかっていた処理が3〜4分に短縮された
      - ただし冗長性がなく、管理コストが課題として残っている
  - 管理画面はVercel、認証・DB・バックエンドはSupabaseで構築している
- [MediaConvertを利用した動画の自動変換環境をCFnでつくってみた](https://dev.classmethod.jp/articles/mediaconvert-s3-auto-convert-cfn/)
  - 背景
    - 「S3にMP4をPUTすると、MediaConvertでHLS形式に自動変換する」というシンプルな構成をCloudFormation（SAM）で再現可能にしたかった
  - 観点
    - 再現性（IaC）
      - 誰でも同じ環境を再構築できること
    - 検証環境の迅速な立ち上げ
  - 構成
    - InputBucket（S3）にMP4がアップロードされると、S3イベントトリガーでLambda（Python 3.8）が起動する
    - LambdaがMediaConvertのジョブテンプレートを読み込み、create_jobを実行してHLS変換を行う
    - 変換結果（.m3u8 + .tsファイル）はOutputBucket（S3）に出力される
    - S3バケットは入力用・出力用・ログ用の3つに分離されている
  - IaC化のポイント
    - SAM CLIの `sam deploy --guided` で対話的にデプロイでき、MediaConvert・S3・Lambda・IAMロール/ポリシーがすべて自動作成される
    - MediaConvertのジョブ設定JSONはドキュメントが不十分なため、MediaConvertコンソールのGUIでインタラクティブにJSON定義を生成し、それをテンプレートに組み込むのが実践的
  - 残課題
    - エラーハンドリングが未実装であり、ジョブ失敗時の通知やリトライ処理の追加が必要
- [Contentful+Muxによる動画の管理とストリーミング配信](https://aquait.co.jp/topics/6)
  - 背景・課題
    - Webサイトリニューアル時にトップページに動画を配置する必要があった
    - 当初YouTube埋め込みを使っていたが、iframeによるYouTubeサーバーとの通信トラフィックがサイトパフォーマンスを著しく低下させていた
      - 特にスマートフォン環境でWeb Vitalsへの影響が大きかった
    - またContentful（ヘッドレスCMS）のファイルサイズ上限が50MBであり、大きな動画ファイルを直接扱えなかった
  - 観点
    - サイトパフォーマンス（Web Vitals）
      - YouTube埋め込みによる表示速度低下の解消
    - CMS一元管理
      - 動画を含む全コンテンツをContentfulで統一管理
  - 構成
    - ContentfulのMux App（拡張機能）を通じて動画をMuxにアップロード・エンコードする
    - Contentfulには動画のメタデータ（JSON）のみが保持され、動画データ自体はMux側に保管される
      - これによりContentfulの50MB制限を回避できる
      - Contentful上のプロパティの型は「JSON」でなければならず、他の型を選択するとメタデータの保持・取得が正常に動作しない
    - クライアント側ではGraphQL APIでContentfulからMux動画のメタデータを取得し、Video.jsプレイヤーでMuxからストリーミング再生する
  - 成果
    - YouTube iframe排除により第三者サーバーとの通信がなくなり、サイトパフォーマンスとWeb Vitalsが改善した
    - 動画を含む全コンテンツをContentfulで一元管理できるようになった

- [IIJにおけるDRMの取り組み](https://www.iij.ad.jp/dev/report/iir/063/03.html)
  - 背景・課題
    - IIJは動画配信プラットフォーム事業者として、コンテンツの不正コピー・再配布を防ぐDRM基盤を自社開発・運用している
    - 2008年のFlash Video DRMから始まり、PlayReady、Marlin DRMを経て、現在はWidevine・FairPlay・PlayReadyの主要3システムすべてに対応
  - 観点
    - マルチDRM対応
      - Widevine（Chrome/Android）・FairPlay（Safari/iOS）・PlayReady（Edge/Windows）の3システムで全デバイスをカバー
    - 自社開発によるコスト予見性
      - 外部DRMプロバイダを利用しないことで、コストが見積もりやすく、サービスの持続可能性も高まる
    - 標準規格（CPIX）の活用
      - ベンダーロックインを回避し、異なるDRMシステム間の相互運用性を確保
  - コンテンツの暗号化
    - CPIX（Content Protection Information Exchange）規格に基づき、暗号鍵やDRM固有情報をXML形式でやり取りする
    - 各DRMシステムはsystemIdで識別され（例: Widevineは`edef8ba9-79d6-4ace-a3c8-27dcd51d21ed`）、1つのCPIXドキュメントで複数DRMの鍵情報を一括管理できる
    - AWS環境ではSPEKE（CPIXを拡張したAWS独自仕様）がMediaPackage等と連携して同様の役割を果たす
  - コンテンツの復号（ブラウザ側）
    - ブラウザはEME（Encrypted Media Extensions、W3C仕様）を通じてCDM（Content Decryption Module）と通信し、ライセンスサーバーから復号鍵を取得して再生する
    - Widevineはセキュリティレベルが3段階あり、L1（TEEによるハードウェア復号）が最も安全で、L3（ソフトウェア復号）が最も低い
      - コンテンツ提供者はセキュリティレベルに応じて配信画質を制限できる（例: L3端末にはSD画質のみ許可）
  - DRMで実現できる制御
    - 再生許可の条件付与、同時再生デバイス数の制限、画質制御（SD/HD/4K）、HDCP（デジタル出力保護）の要求など
- [AWSで動画コンテンツをDRMする&パッケージング&配信する仕組みを作る](https://qiita.com/daisukeoda/items/9a8924b16c1dafcbc5f9)
  - 背景・課題
    - VOD動画コンテンツにDRM保護をかけてパッケージング・配信する仕組みをAWS上に構築する方法を解説した記事
    - 複数のDRMシステム（Widevine、PlayReady、FairPlay）に対応する場合、各システムごとに異なるインターフェースを実装する必要があり、エンコーダー側の複雑性が課題だった
  - 観点
    - SPEKEによるDRMインターフェースの統一
      - AWS独自のSPEKE仕様により、複数DRMシステムを共通のAPIで扱えるようにし、実装の複雑性を軽減
    - サーバーレスなキーサーバー構成
      - Lambda + API Gatewayでキーサーバーを構築し、運用負荷を最小化
  - 構成
    - MediaPackageがDRM暗号化とパッケージングを担当し、SPEKE仕様に則ってLambda製キーサーバーに暗号鍵を要求する
    - キーサーバー（Lambda + API Gateway）はCPIX XMLを処理し、暗号鍵・初期化ベクトル（IV）・キーURL等を返却する
    - 暗号鍵はS3に保管され、再生時にプレイヤーがCloudFront経由でキーを取得して復号する
    - 本記事ではHLS AES-128暗号化を実装しているが、SPEKEはWidevine・PlayReady・FairPlayにも対応可能
  - 実装のポイント
    - MediaPackageのエンドポイント設定でResource ID・System ID・キーサーバーURLを指定するだけでDRM暗号化が有効になる
    - SPEKEリファレンスサーバー（AWS Labs公開）をCloudFormationでデプロイすれば、検証用のキーサーバーを即座に立ち上げられる
    - HLS AES-128のSystem IDは正式な規格がないため、任意のUUID値を使用する
