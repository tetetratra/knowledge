      - `(-> (_a) ~~~)`みたいにする
      - でも不格好
- 継続のバグ
  - 別の世界の(= 別のVMの)クロージャをこっちのVMに持ってきて使う、みたいなことをし始めるとバグりそう
  - 継続オブジェクトは、変数（環境）は持っていない
    - 継続オブジェクトの環境は無視してOK
  - 継続でクロージャを返すときバグってる
```lisp
(= flag 0)
(= closure (callcc (-> (continuation)
  (= x 10)
  (= getx (-> () x))
  (continuation getx)
)))
(if (== flag 1)
  0
  (~
    (= flag 1)
    (p (closure))
  )
)
```

```ruby
require "continuation"
flag = 0
closure = callcc { |continuation|
  x = 10
  getx = -> { x }
  continuation.(getx)
}
if flag == 1
else
  flag = 1
  p closure.()
end
```

`closure`のenv_parent_numが自分自身を指してしまう
 継続の作成時にはまだ作られていなかったスタックフレームを、継続の呼び出し時に返したクロージャが指していると、そんなスタックフレームは存在しないのでバグになる
 → 継続の呼び出し時、継続のVMと現在のVMの**両方**のスタックフレームをマージして使う

毎度GCすると継続を使ったコードがエラーになる
 継続に入っているVMが参照しているスタックフレームのことを無視して（消したりして）いるから

[スタックフレーム]の集合をHashで表現していて、スタックフレームへの参照は全部その数値への参照にしているからバグが起こる？

スタックフレームが親を直接持つようにする（番号を使わずに参照するようにしてみる）
  - だめだった
  - クロージャを作るときに、クロージャを作った瞬間の変数を保持してしまい、クロージャが指し示す環境を更新できなくなった
  - 継続間のスタックフレームの識別子も無くなって、その実装も大変になりそう
 普通に見通しも悪くなるから直接持つ方式はしない

変数が参照しているクロージャが指しているスタックフレームを消してはいけないのはもちろんだけれども、評価スタックに乗っているクロージャのスタックフレームも消してはいけない
 関数や継続からのリターン時に、その返り値を利用することがあるから

継続オブジェクトをGC時に考慮する
 Continuationが持っている別のVM内の変数や実行スタックが、現在のVMのスタックフレームを参照しているかもしれない
