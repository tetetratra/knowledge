# 巨大に膨らむ圧縮データは展開後のサイズ確認では防げない

- 小さな圧縮データを送り、受け側が展開したときにメモリを使い果たさせる攻撃がある。解凍爆弾や zip 爆弾（decompression bomb）と呼ばれる
- Deflate は、ZIP・gzip・PNG・HTTP の圧縮転送（`Content-Encoding: gzip` / `deflate`）などで広く使われている、標準的な圧縮の方式（[RFC 1951](https://www.rfc-editor.org/rfc/rfc1951)）
  - ZIP や gzip は「ファイルの入れ物」の形式で、中身のデータの圧縮には Deflate を使っている
- Deflate は「何バイト前から何バイトをコピー」という短い指示で繰り返しを表す。1回の指示で最大258バイトをコピーできる
  - 例：`abcabcabcabc` は、`abc` のあとに「3バイト前から9バイトをコピー」という指示を置くだけで表せる
  - 同じ1文字を並べたデータは、最大でおよそ1032倍まで縮む（[zlib Technical Details](https://zlib.net/zlib_tech.html)）
  - そのため、180KB の圧縮データが展開すると約180MB になる。普通の XML は数倍しか縮まない
- 展開し終えてからサイズを確かめても防げない。確かめる時点で、展開した分のメモリはもう確保されている
  - 防ぐには、展開する前の入力サイズを絞るか、上限を超えた時点で展開を打ち切る
- SAML では、メッセージの運び方（バインディング）によって、圧縮するかどうかが決まっている（[SAML 2.0 Bindings](https://docs.oasis-open.org/security/saml/v2.0/saml-bindings-2.0-os.pdf) 3.4.4.1 節・3.5.4 節）

| バインディング | 運び方 | 主に運ぶもの | 符号化 |
| --- | --- | --- | --- |
| HTTP-Redirect | URL のクエリに載せてリダイレクト | SP → IdP の AuthnRequest | XML → Deflate で圧縮 → Base64 → URL エンコード |
| HTTP-POST | 自動送信されるフォームで POST | IdP → SP の SAMLResponse | XML → Base64（圧縮しない） |

  - Redirect で圧縮するのは、URL の長さに制限があるから。POST の本文は大きなデータを運べるので圧縮しない
  - 受け側が両方の形式を受け付けて展開を試すと、本来圧縮しない経路でも展開が起き、攻撃の入口になる
- 入力サイズの制限で止まるのは「小さな入力を大きく膨らませる」攻撃だけ
  - 小さいままの XML でパーサーの弱点を突いて重くする攻撃は、パーサーの更新で塞ぐ
  - 大量のリクエストで押す攻撃は、レート制限など別の層で受け持つ
