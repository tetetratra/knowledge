# プロジェクトマネジメント

- 期限といっても色々
  - 実装完了日
  - QA完了日
  - リリース日
- 開発のタスクはすべてissueに残す
- とく大きなissue, プロジェクトは進捗がわかるような形式にしておく
- 業種とか中身ベースよりも、**目的ベース**でタスクを一覧化した方がよい
  - 作業ベース(手段)で一覧化すると目的が見失うことが多い
  - 自分自身に割り振られたときは、最初に目的ベース、次に作業ベースで整理するのが良い
- タスク管理は「タスク単位で割り振る」と「人単位で割り振る」の2種類の方式がある
- 共有したいことはコメントやslackに**文字に**残し、毎日の定例などではそのことを**伝える場**にする
- 親issueからは子issueへのリンクを貼るだけ、が良さそう
  - issueの詳細をどっちに書けばいいかどうか迷うことが無くなるため
- プロダクト開発の視点でタスクを進める
  - バグfixのタスクを担当したときの例
    - 取れる選択肢を考える (プロダクト的な視点で考える)
      - 直す以外に、機能を捨てるという選択肢なども勘案してみる
    - コスパ等を考慮して選択を決定する
    - ↑の選択肢を他の人に相談するときは、背景と共に自分の考えを伝えるのが良い
- スクウェア・エニックス ゲーム開発 プロジェクトマネジメント講座
- プロジェクトの理想形(社内資料)
  - PM・企画といっても色々
    - プロダクトマネージャー(PdM)
      - サービスの方針を考える
    - プロジェクトマネージャー(PjM)
      - スケジュールを考える
    - 開発企画
      - 開発の仕様書作成
      - 各工程の工数を担当者に考えてもらう
        - スケジュール作りはPjMの仕事
    - 運用企画
      - (運用で提供するための)コンテンツを考える
  - 工数出し
    - ガントチャートで整理するのがわかりやすそう
    - 何が何をブロックしているのか・何と何は並行で行えるのかがわかる
- 開発のタスクには「事業」と「サーバー改善」という分類がある
  - 「事業」タスクの合間合間に「サーバー改善」タスクをするのが一般的
- タスクを振られたらスケジュールを確認しよう
  - 締切はいつか
  - 実装を終えていたい日はいつか
    - リリース日から逆算する
    - `実装を終えていたい日 = リリース日 ー (レビューの日数 ＋ QAしてもらう日数)`
  - 確保できる営業日を概算
    - スケジュール的に無理そうなら相談
- タスク(issue)を振られたら終了(close)条件を明確にしよう
  - 決められていなければ自分で考える
  - タスク忘れが減る
- 期限があるタスクの実装に、既存コードのリファクタリングを含めるのは、締め切りの観点から危ないことが多い
- パーキンソンの法則にならないように、締切は2つ設けよう
  - >仕事の量は、完成のために与えられた時間をすべて満たすまで膨張する
  - やらねばいけないタスクも見えてくる
- プルリクの着手前(設計段階)や途中(テーブル定義, 実装)で適宜レビューしてもらうとよい
- ややこしい機能の着手はじめは、一旦エンジニア間で会議をして、実装方針等の相談をするとよい
- 本当にその改修はこのissueのものなのか? というのを意識する
  - 仕事を増やしてしまっていないか? を考える
- **機能**で整理して、**誰**が担当するか、という整理をするとよい
  - 特に複数領域(サーバー and アプリ and 運用 and PM など)にまたがるタスクを扱うときに
- なにかをまとめているissueのコメントなどを更新したときは、更新したことをコメントするとよい
  - >例「ooについて追記/修正しました (リンク)」
- 機能を開発する時の流れ
  - 要件
  - 必要なこと・懸念点等の調査、洗い出し(app, server各々)
  - 仕様を決定する
    - PMの人が、調査を元に大枠の方向性を決定する
    - Engの人が、調査した懸念点とかを元に、細かい仕様を詰めていく
    - まずは画面ベースでまとめして、画面外のことは個別にまとめるとよいかも
  - 工数出し
    - 画面ごととかに何日かかるか
  - 実装
- API設計時にサーバーサイドが中心になって(アプリ側の)懸念点まで考えてしまう状況について
  - アプリ側の懸念とは
    - 「このAPIにこのデータを入れるとキャッシュの制御が要るかも...」みたいな懸念
  - 大まかな流れは変えられない
    - 「DB設計→API設計」という流れなのと、サーバーサイドの制約の方が強いことから、どうしてもはサーバーサイドがAPI設計を提案するという形にはなる
  - 早めに巻き込むことはできる
    - ざっくりとAPI設計を考えた段階でアプリサイドも巻き込んで「API仕様を決める会」を開催して、懸念点を一緒に考える
- 見積もりの肌感覚メモ
  - 設計フェーズ
    - **個人で案出し**
    - **出した案をレビューしてもらう**
      - 難しい案件だと「個人で案出し」の数倍以上かかる
  - 実装フェーズ
    - **実装**
      - 設計済みならさほど時間はかからないはず
    - **レビュー**
      - 実装とレビューで同じくらいの日数がかかる
- 他のタスクを抱えている状況で別のタスクの完了日を聞かれた時は、（他のタスクが）順調に進んだ場合と難航した場合の両方ケースを伝えよう
- タスク(issueを立てるとき)のフォーマット
  - 担当者
  - 期限
  - 方向性
    - やることを具体的(だれがいつまでに何をするか)に書き込む
- 不具合対応について
  - 暫定対応：(手段問わず) 今後同様の不具合が起きないようにする対応
    - 根本原因修正しか手段が無いなら根本原因修正であっても臨時対応になる
  - 恒久対応：長期的な対策・根本的な解決策
- [新規プロジェクトで思い切って開発を進めるためにすべき3つの準備 - Speee DEVELOPER BLOG](https://tech.speee.jp/entry/2024/12/25/183000)
- でかいpjtの親タスクでは、「設計」→「実装」よりも「**方向性決め**」→「**開発**」でフェーズを分けると良い
  - 各開発タスク内で「(詳細)設計」→「実装」という風に進むため
- 「やること」は、「目的ベース」と「手順ベース」で洗い出して、手順ベースの方をチェックボックス化して使っていく
  - というのも、目的の流れ通りに手順が進むとは限らない (行ったり来たりする) から
**例**

```
## やること
### 目的ベース
- 観点の洗い出し
- 調査 (観点ごとに)
- 設計方針の確定

### 作業ベース
- [x]  観点の洗い出し
- [x]  調査 (観点ごとに)
  - [x] アクセスピーク時のアクセス数概算
  - [x] 負荷試験用ツール
  - [x] マシンスペック
  - [x] ...
- [x] 調査結果の共有&相談
- 追加調査
  - [ ] どのようなECSタスクにするか
  - [ ] docker imageの作成・アップロード方法
- [ ]  設計案の検討
- [ ]  設計案の共有&レビュー依頼
- [ ]  設計方針の確定


```
