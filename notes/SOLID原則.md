# SOLID原則

- 単一責任の原則
  - 1つのクラスは1つのことをする
- 開放閉鎖の原則
  - 「オープン・クローズドの原則」とも言う
  - (今後拡張する人が、) 拡張しやすく作る (オープンに作るべき)
  - (自分が今拡張している張本人なのであれば、) 元のコードを書き換えないように作る (クローズドに作るべき)
- リスコフの置換原則
  - 適当なクラスをその子クラスに置き換えたときも、正しく動くように作るべし
  - 継承を使わなければそもそも問題にならない
- インターフェース分離の原則
  - 「クライアントに、クライアントが利用しないメソッドへの依存を強制してはならない」
  - クライアント：インターフェースをimplementする側
  - メソッドへの依存：メソッドを実装すること
  - つまり
    - インターフェースを実装するとき、(インターフェースに定義があるのに)利用しないメソッドがあってはならない
- 依存性逆転の原則
  - > 1. 上位モジュールはいかなるものも下位モジュールから持ち込んではならない。双方とも抽象（例としてインターフェース）に依存するべきである。
    - 上位モジュール：ビジネスロジックなどが当てはまりがち
    - 下位モジュール：viewのロジックとかが当てはまりがち
  - > 2. 抽象は詳細に依存してはならない。詳細（具象的な実装内容）が抽象に依存するべきである。
  - [【SOLID原則】依存性逆転の原則 - DIP](https://zenn.dev/chida/articles/e46a66cd9d89d1) の説明がわかりやすかった
  - [依存性逆転の原則 - Wikipedia](https://ja.wikipedia.org/wiki/%E4%BE%9D%E5%AD%98%E6%80%A7%E9%80%86%E8%BB%A2%E3%81%AE%E5%8E%9F%E5%89%87)
    - > **"反転"** の概念は下位レベルレイヤーが上位レベルレイヤーに依存することを**意味しない**。
    - >**両方のレイヤーは上位レベルレイヤーが要求する振る舞いを表現した抽象に依存**すべきである。
  - 多分こんなかんじ...
    - 普通に作ると`上位モジュール → 下位モジュール`になりがち
      - `上位モジュール`が`下位モジュール`に依存している
      - `下位モジュール`が変化したら`上位モジュール`は壊れてしまうかもしれない状態
**具体例**

```
料理をする → 包丁で切る
料理をする → フライパンで焼く
```

- `上位モジュール → インターフェース ← 下位モジュール`にする
  - `下位モジュール`が提供している機能をインターフェース化する
  - `上位モジュール`は`インターフェース`に依存するようにする
    - `上位モジュール`がDIで`下位モジュール`を受け取るようにする
**具体例**

```
料理をする → i切る ← 包丁で切る
料理をする → i焼く ← フライパンで焼く

```
