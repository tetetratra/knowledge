# 負荷試験環境の構築

- **他システムの事例を調査**
- “負荷 検証 構築 テックブログ” で検索すると丁度いい記事が出てくる。
- 特にインフラ構成についての情報を集める。
  - https://zenn.dev/aldagram_tech/articles/54195274379228
    - 他の検討案
      - seed機能
    - 仕組み
      - (AWS Step Functionsで) 本番相当のデータを自動的に同期する仕組みを構築
        - Auroraクラスターを作成
        - 個人情報のマスク処理
        - DB以外は特に検証環境を作っていなさそう?
    - 運用
      - EventBridgeを用いた定期的な自動実行
        - 週1の間隔で自動実行
  - https://buildersbox.corp-sansan.com/entry/2024/07/25/140000
    - 仕組み・運用
      - 1. GitHub Actionsから負荷試験を実行
      - 2. シナリオファイルを含むDockerイメージをECRにpush
      - 3. k6のCustom resourcesをクラスターに作成
      - 4. k6-operatorが3.を検知し、負荷をかけるJobを作成
      - 5. 任意のAPIに対して負荷をかける（リアルタイムでDatadogにメトリクスを送信）
      - 6. テスト完了後サマリをSlackに通知
    - 負荷のパラメーターも簡単に指定できるような仕組みで構築
  - https://techblog.zozo.com/entry/2024-newwear-load-test-plan
    - 仕組み
      - 試験環境に本番環境を利用(!)
        - 検証専用の環境を作るにあたって、本番相当のDBやデータを揃えるのが難しかったため
      - 単体APIごとと、シナリオを使った負荷試験の両方を試験
    - (本番環境上でやっているので) 負荷量を段階的に増やして試験している
  - https://techblog.zozo.com/entry/2024-newwear-load-test-implemention
    - 発生した課題
      - 負荷試験中にロックが発生
  - https://tech.asoview.co.jp/entry/2023/12/01/093711
    - 仕組み
      - 負荷テストのときのみ、STG環境を本番相当のスペックに変更してテストしている
    - 運用
      - テストシナリオを作成してコミット
      - Argo Workflows (Kubernetes上で動くなにかツール) の画面上から都度実行
  - https://qiita.com/gold-kou/items/e88070f147108512e2af#%E8%B2%A0%E8%8D%B7%E8%A9%A6%E9%A8%93%E7%92%B0%E5%A2%83
    - 確認項目
      - レイテンシ
      - 垂直スケーリングすると線形にスループットが増えるかどうか
    - 仕組み
      - stg環境(prd環境とほぼ同じ構成)を利用
        - テスト中はオートスケーリングしないように設定
    - 運用
      - stg環境は1個しかないので、チーム間で調整して都度実行
  - https://speakerdeck.com/5st7/da-gui-mo-sahisunofu-he-shi-yan-wogai-shan-siteitutahua?slide=13
    - 記事版: https://zenn.dev/qubena/articles/2ad3f468a7c70f
    - しくみ
      - 別途負荷検証環境を構築
      - 本番DB同等のデータを匿名化して利用
    - 改善したこと
      - 実施手順を減らした
      - ダッシュボードを用意した
      - 手動に加えて自動でも負荷試験が行われるようにしていた
  - https://techblog.recruit.co.jp/article-654/
    - もともと負荷試験用DBは存在していて、でも使う手順が煩雑だったのでそこを自動化した話

  - https://tech-blog.yayoi-kk.co.jp/entry/2024/12/14/000000

- 負荷テストツール
  - k6
    - k6 cloudは1回のテストで数万円以上かかりそうでコストが高すぎる
    - https://zenn.dev/pharmax/articles/98ed49994cdaf2
      - Grafana k6 Browser Recorder , har-to-k6 といったツールで、ブラウザの操作をそのままシナリオテストにできそう
    - https://grafana.com/blog/2021/01/27/k6-vs-jmeter-comparison/
      - メモリ消費もk6の方が少ないらしい
  - JMeter
    - xmlファイルでシナリオ書くの難しそう…
    - GUIを使う場合、手元にjava実行環境 & JMeter をインストールしてもらう必要がある
