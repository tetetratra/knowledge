# CPU負荷は量と独占と場所に分けて考える

- 重い処理のリスクを「CPU 使用率が上がるか」だけで判断すると、見落としが出る。量・独占・場所の3つに分けて考える
- **量**：処理時間と、CPU 使用率の上昇幅
  - 対策：1行あたりの処理を軽くする。加工（整形や結合）を SQL に寄せる
- **独占**：同じプロセスのほかの処理を待たせること
  - CRuby では GVL（Global VM Lock）のため、1つのプロセスで同時に Ruby のコードを実行できるスレッドは1本だけ
    - スレッドは I/O 待ち（DB や HTTP）に入るときに GVL を手放す。CPU だけを使う処理は、タイマー（100ms）で切り替えられるまで持ち続ける
  - **CPU 使用率のメトリクスが低くても起きる**
    - CPU を使う重いリクエストが1本あるだけで、同じプロセスのほかのリクエストが遅くなる
    - 待たされたリクエストは処理を始めてから GVL を取り合うので、キューでの待ち時間には表れない
  - Puma のスレッド数を増やしても、並列度は上がらない。並列に動かすなら、プロセス（worker）を分ける
- **場所**：その計算をどのプロセスやサーバーで動かすか
  - 対策：Web のプロセスからジョブ用のプロセスに移し、利用者のリクエストへの影響を切り離す
- あわせて見る項目：メモリ、Web サーバーのスレッドを占有する時間、DB の CPU 使用率
