# ナレッジ振り返り

現在の会話を振り返ってユーザーの学びを抽出し、ローカルにあるナレッジリポジトリをどう変えるかの変更予定を立てる。

このスキルの責務は変更予定を立てるところまでとする。ファイルの作成・更新は行わない。実際にどう反映するかは、このスキルを使う側が決める。

## 手順

### 1. 学びを抽出する

会話を最初から読み返し、ユーザーが得た学びを洗い出す。

ここでいう学びは、**名前のあるもの**（技術、ツール、プロトコル、ファイル形式、用語、概念）について、ユーザーが新しく知ったことである。ナレッジリポジトリは、ものの名前で引く用語集に近い。そのため、どの名前のページにも置けない知識は、内容が正しくても抽出しない。

抽出するのは「やったこと」ではない。作業の記録や、その場の問題を解決した手順は学びではない。ノートは量より質を重視するため、候補は厳しく絞る。学びが1件も残らなくてもよい。

価値が高いのは、そのものが何であり、どういう仕組みや構造で動いているかの理解である。何がどう組み立てられているか、何がどこに置かれてどうつながっているか、何がどこで解釈・実行されるかといった理解は、古くなりにくい。逆に、手順、オプションの一覧、症状と対処の組み合わせは、必要になったときに調べれば分かり、ツールの更新で古くなりやすいので価値が低い。

- 抽出してよいもの
  - 名前のあるものが何であるか、何のためのものか
  - 名前のあるものの仕組みや構造（ファイル形式の中身、データの流れ、内部の構成、実行環境の境界など）
- 抽出しないもの
  - 作業していたリポジトリやプロジェクト固有のコード、設定、構成、命名
  - 社名、サービス名、顧客、社内の事情など、特定の組織に結びつく情報
  - 認証情報、URL、パス、データなど、外部に公開できない情報
  - 設計の方針、進め方、整理の型、検証のやり方、手順。「〜するときは〜する」「〜は〜に分けて考える」「〜は〜で決まる」のような教訓の形になるもの
  - 作業していたシステムの設計の議論を、一般化しないと成り立たないもの。固有の要素を取り除いて抽象的な教訓に作り替えない
  - ソフトスキルの知見（進め方、コミュニケーション、考え方など）
- 外部に公開してよい候補でも、次のどれかに当てはまるものは対象外にする
  - 些末なもの：コマンドやAPIのオプション・引数の一覧、使い方のコツ、特定の症状への対処法、言語の細かい文法の違いなど、調べれば分かり、覚えていなくても困らないもの。仕組みの理解が伴わない「こうすれば動く」という知識もここに入る
  - 一方、同じツールの話でも、それがどういう構造で動いているかの理解は些末ではない。候補がツールの話題なら、オプションや手順を取り除き、仕組みの部分だけを残せないか検討する
  - 既知のもの：一般によく知られた原則や定石を、そのタスクに当てはめただけのもの
  - ユーザー自身が出したもの：ユーザーが会話を主導して決めたこと。ユーザーが教えた側なので、ユーザーにとって新しい気づきではない
  - AI が参考にしただけのもの：AI が調査や作業の途中で調べて書いた情報のうち、ユーザーが質問も反応もしていないもの。AI の発言やツールの出力に書いてあるだけでは、ユーザーの学びではない
  - AI 側の学び：AI が取り違えたことや、AI の調査でつまずいた点から出た注意
  - 狭い実装の癖：特定のライブラリの内部の作りで、知っていても高速化などの小技にしか使えないもの
- ユーザーの学びだと言える根拠は、ユーザーの発言に求める。次のどれかがある事柄だけを候補にする
  - ユーザーが「〜とは何か」「なぜ〜なのか」のように質問した
  - ユーザーが説明に対して納得や驚きを示した、自分の言葉で言い直した、認識を改めた
  - ユーザーが「学び」「覚えておきたい」と言った（これは優先して候補にする）
- 残すかどうかは、候補ごとに次の4つの問いで判断する。すべてに自信を持って「はい」と答えられるものだけを残す
  - これは何という名前のものについての知識かを言えるか。その名前は、用語集の見出し語になるか
  - 数か月後にその名前でページを開いたとき、ここに書いてあってほしい内容か
  - ユーザーにとって新しい気づきや、認識が改まった点か。根拠になるユーザーの発言を挙げられるか
  - 教訓、注意書き、手順、整理の型ではないか
- 固有の議論の中に、すでに世の中で名前の付いている概念や技術が出てきて、ユーザーがそれを新しく知った場合は、その概念や技術のページとして書く。議論そのものは書かない
  - 例：ある画面の設計を話す中で「楽観的ロック」を初めて知ったなら、楽観的ロックが何であり、どう動くかを書く。その画面でどう使うと決めたかは書かない
  - 例が必要なら、新しく書き起こした最小限の例を使う
- 会話で確かめられていない推測（原因の推測など）は、できるだけ自分で公式ドキュメントなどの信頼できる情報源を調べて確定させる。確定できた場合は本文に出典を添える。確定できなければ、その学びまたはその部分を対象外にする
- 誤りだと判明した内容は学びに含めない
- 学びが見つからなければ、無理に作らずその旨を伝えて終える

### 2. 反映先を決める

ノートは、単語、概念、もの単体のページとして持つ。学びごとに、まず「何という名前のものについての知識か」を決め、その名前のページを反映先にする。

- その名前の既存ノートを、表記ゆれ（英語と日本語、略称と正式名称、空白やアンダースコアの有無）も含めて探す。あれば、そのノートへの追記にする。追記する位置（どの見出しや箇条書きの下か）も決める
  - ぴったりの名前のノートがなくても、それを含む上位のもののノート（例：あるミドルウェアの設定項目なら、そのミドルウェアのノート）があれば、そこへの追記にする
- 既存ノートにすでに同じ内容があれば、その学びは変更予定から外す
- 該当するノートがなければ、そのものの名前で新しいノートを作る
- 主張や気づきを題にしたノートは作らない。主張は、そのもののページの中の箇条書きとして書く
  - 悪い例：「楽観的ロックは更新時にバージョンを比べて競合を見つける」というノートを作る
  - 良い例：「楽観的ロック」というノートに、その仕組みを箇条書きで書く
- 複数の学びが同じものについてなら、1つのノートにまとめる
- 名前を決められない学びは、変更予定から外す

### 3. 本文を書く

読む側が疲れないよう、本質的な情報だけに厳選する。量が多いほどよいのではなく、必要十分であることを目指す。

- 分量の目安
  - 小さい学び：数行
  - 普通の学び：10行程度
  - どうしても足りないときだけ：20行程度
- 単独で読み返しても意味が分かるよう、主語と対象を明確にする
- 新しいノートは、冒頭の1〜2行で「それは何か」を書き、続けて今回分かったことを箇条書きにする
- 既存ノートへの追記は、そのノートの書き方（箇条書きの階層、文体）に合わせる
- 新しいノートは、ナレッジリポジトリの既存ノートと同じ形式にする。リポジトリにルールを記した文書（`AGENTS.md`、`README.md` など）があれば従う

### 4. タグを決める

- 既存ノートで使われているタグを調べ、合うものがあればそれを使う。表記ゆれのある新しいタグを作らない
- 合う既存タグがなければ、新しいタグを作る
- 1つのノート内でタグを重複させない
- 既存ノートに追記する場合は、追記内容に合わせてタグの追加が必要かも検討する

### 5. ファイル名を決める

新しいノートのファイル名は、そのものの名前（名詞）にする。文にしない。

- 空白と記号を使わない。記号や空白が入ると、ファイルを扱うさまざまなアプリで壊れるため
  - 使ってよい文字は、日本語、英数字、ハイフン（`-`）、アンダースコア（`_`）に限る
  - 名前に空白が入るものは、アンダースコアでつなぐ
- 既存ノートと名前が重複しないことを確認する
- 既存ノートのファイル名は変更しない

## 出力

指定がなければ、変更予定を会話に出力する。出力先や形式の指定があれば、その指示に従う。

変更予定には、学びごとに次の内容を含める。

- 学びの要約（1行）
- 何という名前のものについての知識か
- 根拠にしたユーザーの発言（1つ。短く引用する）
- 反映方法：新規作成か、既存ノートへの追記か
- 対象ファイル：新規ならファイル名、追記なら既存ノートのパスと追記位置
- タグ：使う既存タグと、新しく作るタグを区別して示す
- 本文の案：そのまま反映できる形で書く

最後に、抽出を見送った学びがあれば、その理由（名前を付けられない、ユーザーが反応していない、リポジトリ固有、公開できない情報など）を短く添える。
